Nectar IoT Data Platform — Architecture

Kafka → Delta Lake medallion → star schema, with a streaming path for latency and a batch path for truth.

1 · Edge & ingestion
IoT devices
Chillers, AHUs, pumps, boilers, UPS, sensors.
5-minute nominal sampling, irregular in practice.
Edge gateway
Buffers through network outages, batches and retries.
At-least-once — duplicates and late arrivals are normal.
Kafka
iot.telemetry.raw · 6 partitions
iot.events.raw · 3 partitions
Keyed by asset_id; 72 h retention = replay window.
Asset registry
Sites, buildings, assets and parent_asset_id.
Authoritative for topology and referential integrity.
▼   two read paths, one source of record
2 · Processing
Spark Structured Streaming — seconds
Event-time windows · watermark 15 min · checkpointed exactly-once.
Dedupe within the watermark; 5-minute rollup for the live dashboard.
Fast and approximate.
Spark batch (Airflow, hourly) — authoritative
bronze → silver → gold → hierarchy → serving.
Idempotent MERGE on the business key; restates whatever the stream approximated.
Slow and correct.
Dead letter queue
Payloads that are not valid JSON cannot be validated by a rule — there is no record to evaluate. Raw bytes + reason are kept so the stream never blocks on one bad producer.
Shared rule set
The same Rule objects run in both paths (nectar/quality/rules.py), so streaming and batch cannot drift apart.
▼
3 · Lakehouse — Delta Lake on object storage
Bronze — as received
Every column a string, plus lineage (_ingest_id, _source_file, _payload_hash).
Partition ingest_date. Append-only, replayable.
Silver — trustworthy
Cast · enrich · validate · dedupe · MERGE.
Partition event_date, Z-ORDER asset_id.
Gold — consumable
Star schema, curated marts, site/building/asset roll-ups, closure table.
Partition event_date.
Quarantine — not dropped
Rows failing a BLOCKING rule, tagged with the rule ids they broke and the batch that rejected them. Replayable after the upstream fix.
dq_results — quality as data
One row per (batch, table, rule) with counts, thresholds and verdict. "Which site's data degraded this week" is a SQL query.
▼
4 · Serving
SQL warehouse
Databricks SQL / Snowflake external tables over the same Delta files — no copy, no drift. DuckDB locally.
Dashboards
Site & asset metrics, energy trends, fault statistics, live 5-minute rollup.
REST API
/sites/{id}/energy · /assets/{id}/health · /sites/{id}/assets
ML / feature store
Atomic grain retained; SCD2 + time travel give point-in-time-correct, reproducible training sets.
5 · Orchestration & observability — spans every layer
Airflow
Hourly DAG with catchup, max_active_runs=1, exponential retries, per-task timeouts, SLAs. Nightly maintenance DAG for OPTIMIZE / VACUUM / late-arrival restatement.
Quality gate
A BLOCKING breach fails the gate and downstream tasks skip — stale beats wrong. The report still runs, because a failed batch is when it matters most.
Signals
Per-asset freshness watermark · rule pass rates · consumer lag & state size · JSON logs carrying batch_id end to end.
Alerting
SLA miss ⇒ warn (dashboards stale). Failure ⇒ page (dashboards wrong), with the quarantine query for that batch in the message.
Edge & ingestion Processing Storage Serving Orchestration Failure handling
The central trade-off. The streaming path answers “what is happening right now” and the batch path owns “what actually happened”. Reconciliation between them is not a nightly surprise — it is the design. Both run the same validation rules from the same module, so the two answers differ only in latency and completeness, never in definition.
